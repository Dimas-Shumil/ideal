# Этап 13 — Web Push

Дата: 24 октября 2026 года. Основа: архив пользователя после commit `48475d3`.
Результат — ZIP-патч, без коммита/push и без перехода к этапу 14.
Актуальные правила: `docs/PUSH.md`.

## Сделано

- Новые PushSubscription/PushDelivery и одна добавочная миграция.
- VAPID через серверное окружение, локальный безопасный генератор в новый файл вне проекта.
- Подписки нескольких устройств, строгий endpoint/key DTO, запрет чужого endpoint,
  session/role/authVersion/CSRF/Origin/rate-limit и аудит подписки/отзыва.
- Точечные hooks четырёх событий расписания, outbox в бизнес-транзакции.
- Worker в существующем Node, PostgreSQL lease/claim, ограниченные retries,
  404/410 cleanup, независимые устройства, срок хранения, безопасные логи.
- Защищённая страница уведомлений, ссылки из рабочих панелей, SCSS и готовый CSS.
- Push-only service worker с allowlist переходов текущего origin.
- Смена доступа через userService отзывает подписки; перед отправкой повторно
  проверяются active/role/authVersion. Клиентский кабинет, PWA и магазин не добавлены.

## Реально выполненные проверки

Контейнер: Node 24.22.1, npm 11.9.0, временный PostgreSQL 18.4 (не Windows-среда пользователя).
Зависимости из lock установлены; Prisma schema validate и generate прошли.

Полный финальный `npm test`: **94/94 PASS**, 0 fail/skip/cancel.
Все прежние 69 тестов сохранены; в старом schema-тесте список таблиц расширен
двумя Push-таблицами. Добавлены 25 тестов Push/SW. Production limits не ослаблялись.
Runner дважды выполнял migrate deploy: повторное применение не добавляет миграций.

Новая миграция проверена на отдельной `ideal_auth_test` с тремя прежними миграциями.
До/после сравнены полные JSON-строки контрольного User и Client: без изменений.
Это проверка контрольных записей, не заявление о проверке реальной БД пользователя.
`ideal_dev` пользователя не подключалась и не изменялась. Прежние три SQL-миграции
сверены с загруженным архивом побайтово, не изменены.

Проверены node --check всех изменённых/новых JS/MJS, компиляция SCSS в CSS,
VAPID конфигурация (пустая/валидная/частичная/несогласованная пара), whitespace diff.

Chromium: **24 сценария**, OWNER/ADMIN/TRAINER × 1440/768/390/320 px × JS on/off,
0 page errors. Вход, ссылка из панели, страница уведомлений, отсутствие горизонтального
переполнения, серверная HTML-форма отзыва. В сценариях JS Permission API подменён:
проверены отсутствие автоматического запроса и вызов по кнопке. Системное разрешение
и реальная браузерная подписка этими сценариями не проверяются. Desktop/mobile
скриншоты визуально просмотрены; они временные и в ZIP не включены.
SW JSON/переходы проверены отдельно через VM-тесты, transport — внедряемый fake send.

Первый прогон выявил ожидаемое расширение таблиц в старом schema-тесте и ошибку
PostgreSQL `unexpected data beyond EOF` на временной overlay ФС. Тестовый кластер
перенесён в tmpfs, очищена повреждённая пустая тестовая таблица CrmEvent. После этого
полный прогон прошёл 91/91; после дополнительных сценариев очереди — финальные 94/94.
Рабочие данные пользователя и его БД не затрагивались.

## Не проверено / ограничения

- Реальная отправка через FCM/Mozilla/Apple/WNS, системные notification/click,
  реальные телефоны, Safari/iOS, HTTPS/Nginx и производственное окружение.
- Ручная приёмка пользователя на Windows и PostgreSQL 18.6.
- Полный повторный визуальный прогон публичных анимаций: их файлы не менялись.
- Exactly-once через сеть не гарантируется при падении после provider acceptance;
  стабильные topic/tag уменьшают повторы. Replay POST не дублирует outbox.
- Клиентский Push ждёт клиентской авторизации. Напоминания не включены.

## Приёмка

Сначала `npm ci`, `npm test` на отдельной test БД. Только после успеха deploy/generate/status
для dev и ручная проверка. VAPID настроить по `docs/PUSH.md`; существующий `.env`
не заменять. Удалений файлов нет. Git-команды, коммит и push — после локальной приёмки.
