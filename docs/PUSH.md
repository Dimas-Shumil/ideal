# Web Push — этап 13

## Границы и события

Реализовано для существующих User OWNER/ADMIN/TRAINER. CLIENT не добавлен в Role:
без клиентской авторизации безопасной клиентской identity пока нет. Будущий кабинет
должен определить её и отдельные guards до подписки. Фиктивных пользователей нет.
Демо-магазин, публичный frontend и PWA не меняются. Напоминания не включены;
`availableAt` позволяет позже добавить запланированную доставку без внешней очереди.

Тренер получает новую запись, отмену записи, отмену и перенос только своего занятия.
Даже собственная запись тренером создаёт уведомление: это согласованная категория,
а не произвольные события CRM. Создание занятия, посещение и NO_SHOW не рассылаются.
OWNER/ADMIN получают только отмену/перенос занятия, в котором до операции были
BOOKED (для отмены также ATTENDED); автор операции исключён. Это рабочий сигнал
о необходимости связаться с клиентами, пока клиентских уведомлений нет.
Пустые занятия, новые записи, платежи, правки клиентов не создают административного шума.
TRAINER не получает данные чужого занятия. Причины, название занятия, ФИО, телефоны,
финансы, CRM-комментарии и внутренние ID занятия в payload не включаются.
Уведомление содержит категорию, дату/время Asia/Krasnoyarsk и ссылку в защищённый список.

## Настройка VAPID

Все три переменные задаются вместе: `PUSH_PUBLIC_KEY`, `PUSH_PRIVATE_KEY`,
`PUSH_SUBJECT` (реальный `mailto:` контакт или публичный HTTPS URL).
При пустых значениях сервер и основные операции работают, отправка выключена.
Ключи генерируются один раз, не на каждом старте. Не менять ключи без плановой
переподписки устройств. Для локального оператора из корня IDEAL на Windows:

```bat
node tools/generate-push-keys.mjs ..\ideal-push-private.env
```

Создаёт НОВЫЙ файл вне проекта; существующий не перезаписывается, ключи не печатаются.
Заполнить `PUSH_SUBJECT` и вручную перенести эти три строки в существующий серверный
`.env`, сохранив остальные переменные. Файл с ключами хранить приватно, не коммитить,
не отправлять в чат/архив. На Windows проверить права доступа к этому файлу.
Публичный ключ доступен авторизованному браузеру через `/api/push/config`;
private key никогда не передаётся в HTTP или журналы.
После изменения env перезапустить приложение. `web-push` закреплён на 3.6.7.

## Устройства и доступ

`/notifications` доступна всем трём ролям, ссылка есть в рабочих панелях.
Разрешение запрашивается исключительно кнопкой пользователя. Проверяется разрешение
браузера и серверная регистрация именно текущей identity. До кнопки service worker
не регистрируется; существующая регистрация лишь проверяется.
Есть включение, отключение текущего устройства и серверный отзыв всех подписок
через обычную HTML-форму (работает без JS). Разрешение браузера сервер удалить не может.
Нет автоматической переподписки после отзыва всех устройств.

Каждое устройство — отдельная строка. Endpoint уникален глобально, максимум 20 устройств
на пользователя. Повтор регистрации не создаёт дубль; чужой endpoint не переносится
между аккаунтами даже для OWNER. На общем браузере сначала отключить Push в старом
аккаунте. Если доступа к нему нет — нажать «Сбросить подписку браузера», затем включить
уведомления заново. Сброс вызывает browser unsubscribe только по явному действию,
не удаляет чужую серверную запись и не переносит endpoint между аккаунтами.
Прежний endpoint будет удалён worker при ответе 404/410. Альтернатива — удалить
данные/разрешение сайта в браузере и создать новую подписку.
Logout сам по себе не отзывает подписку: уведомления предназначены и для закрытого
кабинета. Об этом есть текст на странице настроек. Не включать на общем устройстве.
Деактивация, изменение роли или пароля через штатный userService удаляет подписки
и каскадно очередь. Worker повторно проверяет active/role/authVersion перед отправкой,
поэтому прямое изменение этих полей БД тоже не продолжает старую доставку.
Уже переданное провайдеру/устройству сообщение отозвать невозможно.

Page и API имеют собственные auth/role guards. Мутации: действующая сессия,
CSRF + точный Origin, лимит 60 запросов/15 минут/user, строгий DTO без userId.
Мутации подписок под общим accessLock повторно проверяют identity и запись сессии.
Endpoint перед отправкой проверяется по HTTPS allowlist FCM/Mozilla/Apple/WNS,
без портов, credentials и fragment; произвольный адрес или IP не принимается.
Ключи проверяются по длине/base64url, p256dh — как точка P-256.
Поддержка другого провайдера требует отдельного подтверждённого добавления hostname.

## Очередь и эксплуатация

Существующая бизнес-транзакция сохраняет PushDelivery для каждого текущего устройства.
Ошибка вставки outbox откатывает операцию вместе с аудитом (нет молчаливой потери события).
Сетевой отправки внутри бизнес-транзакции нет. Недоступность Push provider не откатывает
запись/отмену/перенос. Replay key возвращает прежний результат до создания outbox;
дополнительно уникальна пара eventKey/subscriptionId. Новые устройства не получают
события, которые произошли до их регистрации.

Worker в существующем процессе Node выполняется при старте и каждые 15 секунд.
PostgreSQL очередь — источник состояния; interval лишь будит обработчик.
Атомарный UPDATE с FOR UPDATE SKIP LOCKED выдаёт lease на 120 секунд; после перезапуска
незавершённая доставка может быть подобрана снова. Один batch — до 25 устройств;
одна ошибка не блокирует другие. Не более пяти попыток. Повторы только для сети,
429 и 5xx, задержка 30/60/120/240 секунд. Остальные 4xx — FAILED.
404/410 удаляют подписку и её доставки; логи содержат только тип события и HTTP status.
Нет endpoint, ключей, тела provider response или error.message в логах.
Последний успех/сбой записываются в подписку. Сообщения старше суток пропускаются,
строки очереди старше семи суток очищаются при обработке. TTL провайдера 300 секунд.
Нет неограниченных retries или кнопки массовой тестовой рассылки.

Семантика сети — at-least-once в пределах попыток, не обещание exactly-once:
сбой между приёмом провайдером и отметкой SENT может повторить отправку.
Стабильный provider topic и notification tag помогают заменить повтор одного события,
но повтор после уже закрытого уведомления полностью исключить нельзя.
SENT означает принятие провайдером, а не просмотр пользователем.
Временное выключение процесса не теряет строки; для обработки нужен работающий Node.

SW `/push-sw.js` имеет root scope, принимает push/notificationclick, не содержит fetch,
cache/offline/install prompt. URL разрешены только текущего origin и точных путей
`/trainer/lessons`, `/crm/schedule`, `/notifications`, query/hash отбрасываются.
Неверный payload показывает нейтральное уведомление. HTTPS необходим вне localhost.
iOS/Safari и реальные push provider требуют проверки на устройствах после настройки;
этот этап не добавляет manifest или PWA-установку.

## Проверка на Windows — сначала test, потом dev

Сохранить резервную копию рабочей БД штатным способом. Распаковать ZIP поверх IDEAL.
`.env`, данные и node_modules не входят в ZIP. После изменения зависимостей:

```bat
npm ci
npm test
```

Runner сам использует ТОЛЬКО отдельную TEST_DATABASE_URL (`ideal_auth_test` / отдельная
роль `ideal_test`), дважды выполняет migrate deploy и генерирует Prisma Client,
затем запускает все старые и Push-тесты. Нужна настроенная TEST_DATABASE_URL в env.
Нельзя направлять её на dev: тесты очищают тестовые данные.
После успешных тестов применить новую миграцию к существующей `ideal_dev`:

```bat
npm run db:deploy
npm run db:generate
npm run db:status
npm run dev
```

Никаких db push/reset и изменения прежних миграций. Применяется только
`20261024170000_web_push`. Проверьте существующих сотрудников, клиентов,
абонементы и занятия после миграции. Прогон контейнера не заменяет локальную приёмку.

Ручная проверка после настройки VAPID: три роли, два тренера с разными занятиями,
два браузера одного пользователя, явное согласие/запрет, текущий device on/off,
отзыв всех, новая запись/replay/отмена/перенос, отсутствие чужих событий,
отключение сотрудника/смена пароля, переход из notification после logout,
desktop/mobile, клавиатура, режим без JS. Не публиковать секреты в отчётах.
