# Магазин — этап 14

Согласованный объём: публичный серверный магазин, самовывоз, заказ без регистрации,
оплата при получении, ассортимент OWNER и обработка заказов OWNER/ADMIN.
Реализация: 25 октября 2026 года. Этот документ описывает текущие правила; docs/archive/
содержит только исторические отчёты.

## Покупка

Любой посетитель выбирает опубликованный товар и вариант, добавляет в корзину и отправляет
заказ. Имя и телефон обязательны, комментарий необязателен. Принимаются 10–15 цифр телефона,
российский 8 в начале 11-значного номера заменяется на 7. Только самовывоз из клуба.
Сотрудник связывается с покупателем и подтверждает наличие и количество. Онлайн-оплаты,
доставки, клиентского кабинета и автоматического создания CRM-клиента нет.
Способы оплаты при получении: наличные, карта или перевод.

Корзина содержит только UUID вариантов и целые количества в серверной сессии.
Демо-localStorage `ideal-demo-cart-v1` не читается, не импортируется и не удаляется.
Для гостя сохранён прежний pre-auth lifecycle сессии: 15 минут от создания. После истечения
потребуется выбрать товары заново; для авторизованной сессии действуют её idle/absolute сроки.
Вход/выход меняет сессию, корзина через смену identity не переносится. Разные браузеры имеют
разные корзины. Одновременные изменения в нескольких вкладках используют последнее сохранённое
состояние; перед отправкой нужно обновить корзину и проверить состав. Серверная подпись
котировки не допускает оформление при незаметно изменившемся составе, цене или доступности.

Технические лимиты: 30 вариантов в корзине, 99 единиц на вариант, общий итог до 20 млн ₽.
Это не остатки склада. Цена варианта — 0,01–1 000 000 ₽. Деньги — целые копейки.
Сумма строки и итог рассчитываются сервером, цена из браузера не принимается.
Если данные изменились после открытия формы — заказ не создаётся, покупатель проверяет
обновлённую корзину. Оформленный заказ хранит снимок названий/UUID товара и варианта,
количества, цены и итога. Последующие изменения справочника его не меняют.

Повтор того же POST с UUID формы возвращает прежний заказ. Изменённый payload с тем же
ключом отклоняется. Разные формы с разными ключами считаются разными намерениями.
Страница результата доступна только сессии, создавшей заказ. Публичного списка заказов нет.

## Ассортимент и наличие

Справочник изначально пуст. Реальные товары, цены, реквизиты и адрес выдачи не выдумываются.
OWNER вносит название, категорию, описание, характеристики, варианты и фотографии.
Название варианта описывает вкус, фасовку или их сочетание. У каждого варианта одна цена,
свой признак наличия и публикации. Не более 50 вариантов на товар.
Количественный склад, резервы, списания, скидки и промокоды не включены.
Оформление не резервирует товар и не гарантирует количество: это подтверждает сотрудник.
Товары/варианты скрываются с публикации, физического удаления карточек и заказов нет.

`/shop.html`, `/product.html?id=UUID`, `/cart.html` — серверные EJS-страницы.
Категории, пагинация и основные формы работают без JS. Главная получает до пяти опубликованных
товаров из БД, сохраняет Coverflow, drag и клавиатурную навигацию. При одном товаре переключение
не включается; пустой справочник показывает пустое состояние. Демо-файлы shop/product/cart.html
сохранены только как исходники статического Go Live-превью, Express их не раздаёт.
Рабочий магазин запускается через Node.

## Права и статусы

- OWNER: ассортимент, варианты, цены, наличие, публикация, фотографии и заказы.
- ADMIN: список и карточки заказов, статусы, отмена, отметка полной оплаты и выдачи.
  Ассортимент, цены и наличие ADMIN не меняет.
- TRAINER не получает административного доступа к магазину. Публичная покупка доступна ему
  как любому посетителю.

OWNER/ADMIN: `/shop-panel/orders`; OWNER: `/shop-panel/products`. HTML и API защищены независимо
от меню. Навигация меняется через общий `server/views/partials/panel-nav.ejs`.
Статусы: **Новый → Подтверждён → Готов к выдаче → Выдан**. Только последовательные переходы.
До выдачи OWNER/ADMIN могут отменить с обязательной причиной минимум три символа.
Выданный и отменённый заказ окончательны. Возвраты после выдачи в этап не входят.
При выдаче сотрудник отмечает фактически полученную полную оплату и фактический способ оплаты.
Это учёт, не банковская операция. Частичной оплаты и долгов нет; сумма заказа не редактируется.
История сохраняет автора, дату, статус и причину отмены. Критические действия пишутся в AuditEvent.

## Фотографии

Загрузка OWNER через multipart HTML-форму работает без JS. До восьми фото на товар,
по одному за запрос. JPEG/PNG/WebP до 5 МиБ и 20 млн пикселей. SVG, GIF, анимация и
некорректные байты не принимаются. sharp декодирует фактический формат, поворачивает по EXIF,
уменьшает до 1600×1600 без увеличения и перекодирует в WebP без исходных метаданных.
Результат до 1 МиБ хранится в PostgreSQL и входит в штатный pg_dump. Исходное имя и путь
не сохраняются. Выдача только с фиксированным image/webp и nosniff.
Фото скрытого товара видит только OWNER. При удалении фото удаляются и его байты.
Порядок — по загрузке, первое фото обложка. Чтобы заменить обложку, загрузить новую и удалить
прежнюю. Отдельная сортировка перетаскиванием не входит в этап.
Зависимости закреплены: busboy 1.6.0, sharp 0.35.5. npm ci устанавливает платформенный бинарный
пакет sharp, в том числе для Windows x64; не использовать --omit=optional.

## Защита и конкурентность

Строгие DTO, серверная валидация, auth/role guards, CSRF и точный Origin на всех POST.
Публичная корзина: 90/15 минут/IP; оформление: 10/15 минут/IP. Административные мутации:
120/15 минут/user; фото: 16/15 минут/user. Общий лимит приложения сохранён.
Мутации каталога и заказов используют общий accessLock и транзакции, повторно проверяют
active/роль/authVersion и действующую серверную сессию. Версии защищают от потерянных правок.
Авторизованные операции используют прежний журнал CrmOperation с отдельными SHOP_* action
и fingerprint; существующая security-модель не заменяется новым framework.
Оформление, снимок, сумма, история, аудит и outbox атомарны. Уникальный UUID формы и блокировка
не дают одновременному повтору создать второй заказ. Ключ привязан к хешу серверной сессии.
Production rate limits ради тестов не ослабляются.

## Push

Только новый заказ: всем текущим активным OWNER/ADMIN и их зарегистрированным устройствам.
TRAINER события магазина не получает. В payload нет имени, телефона, суммы и состава.
Ссылка `/shop-panel/orders` разрешена в SW; сам раздел защищён входом и ролями.
Правки каталога и статусов уведомления не создают, повтор POST не дублирует outbox.
Сеть выполняется существующим worker после коммита: сбой провайдера не откатывает заказ.
Реальная доставка системного Push по-прежнему не подтверждена.

## Установка на Windows: сначала test, затем dev

Остановить приложение. Сохранить резервную копию ideal_dev штатным способом.
Распаковать ZIP-патч поверх IDEAL с заменой. Существующий `.env` не менять.
Из корня проекта:

```bat
npm ci
npm test
```

Runner применяет миграции дважды ТОЛЬКО на отдельной TEST_DATABASE_URL, генерирует Prisma
Client и запускает прежние и новые тесты. Тестовые данные очищаются. При ошибке dev-миграцию
не применять. После успешного npm test, пока dev-приложение остановлено:

```bat
node tools/shop-data-snapshot.mjs > ..\ideal-before-stage14.json
npm run db:deploy
npm run db:generate
npm run db:status
node tools/shop-data-snapshot.mjs > ..\ideal-after-stage14.json
fc /b ..\ideal-before-stage14.json ..\ideal-after-stage14.json
npm run dev
```

Снимки содержат только число строк и digest прежних бизнес-таблиц; секретов и персональных
данных в них нет. AuthSession и PushDelivery исключены как изменяемые служебные таблицы.
Во время сравнения не запускать worker и не редактировать данные. Применяется только новая
`20261025000000_shop`. Старые четыре миграции не менялись. Не использовать db push/reset.
После миграции проверить прежних сотрудников, клиентов, абонементы, расписание, посещения
и настройки Push. Проверить роли, товары/варианты/фото, заказ, статусы, оплату/выдачу и отмену,
mobile/desktop, клавиатуру и режим без JS. Реальный Push проверять отдельно на устройствах.
Контейнерный прогон не заменяет приёмку на Windows и PostgreSQL 18.6.

Текстовые формы товаров имеют отдельные ограниченные body limits: 128 КиБ URL-encoded,
48 КиБ JSON, до 12 полей. Это позволяет сохранять два описания по 4000 символов UTF-8;
остальные маршруты сохраняют прежний лимит 8 КиБ. Multipart имеет свои ограничения.
Публичные header/footer/menu/dialog берутся из прежних components; sync_components.py
также обновляет соответствующие EJS-partials магазина.
