4. СЕССИИ И ПАРОЛИ
Предложение: проверенный session middleware с PostgreSQL store, cookie хранит
только непрозрачный идентификатор; без JWT в localStorage и без MemoryStore
в production. Store инкапсулировать, согласовать его схему/миграции с Prisma;
не позволять двум инструментам независимо управлять одной таблицей сессий.
Для данного плана AuthSession — логическая сущность store, не требование
написать собственную криптографию. Выбрать конкретный совместимый адаптер
на этапе 8, проверить отзыв всех сессий пользователя и очистку просроченных.

Cookie: HttpOnly, Secure в production, SameSite=Lax, Path=/, без Domain.
Имя отдельное для IDEAL; __Host- префикс только на HTTPS с его требованиями.
В локальном HTTP — отдельная dev-настройка, не отключать Secure в production.
Сменить ID сессии после входа и повышения привилегий, logout — POST с CSRF,
уничтожение store-записи и очистка cookie. Серверные idle/absolute сроки:
предлагаемые 8 часов/7 суток до согласования, без бессрочного remember-me.
Смена пароля/роли/деактивация отзывает все сессии; действительность проверять
на каждом запросе, а не полагаться на роль, сохранённую при входе.
Не доверять X-Forwarded-* вне известного прокси, localhost/127.0.0.1 разных
портов не изолируют cookies по порту — dev-имя должно исключать коллизии.

Пароли: Argon2id, случайная соль через библиотеку, параметры подобрать по
измерению на VPS; верхняя граница ввода и ограничение параллелизма хеширования.
Пароль не обрезать молча; разрешить длинные фразы, проверить Unicode и длину
в байтах. Не хранить временные пароли в файле/аргументах командной строки.
Первый OWNER создаётся CLI с интерактивным скрытым вводом; без seed-пароля
и без публичного bootstrap-endpoint. Команда повторно не создаёт дубль.
До согласования email/SMS восстановление через доступный только оператору VPS
CLI: новый пароль вводится скрыто, сессии отзываются, действие аудируется.
Не выдавать пароль в HTTP-ответе, логах, документах или пользовательском ZIP.

5. ГРАНИЦА HTTP И ЗАЩИТА
Порядок: requestId/лимиты/заголовки → session → auth/CSRF по маршруту →
валидация allowlist → объектная политика → service/транзакция → безопасный ответ.
Аутентификация не заменяет авторизацию. Парсинг login/password имеет лимиты;
одинаковое сообщение для неизвестного пользователя/неверного пароля/блокировки.
Rate limit по IP и нормализованному логину, разумная задержка, без вечной
блокировки чужой учётной записи; при нескольких процессах общее хранилище
счётчиков либо проверенный limiter на прокси. Проверить обход через заголовки.
CSRF-токен привязан к сессии и защищает login/logout и любые изменения;
Origin сверяется с APP_ORIGIN, непроверенный Host не является эталоном.
SameSite — дополнительный барьер. Поведение при отсутствии Origin определить
явно: для браузерных мутаций fail-closed, тесты/CLI используют согласованный протокол.
GET/HEAD ничего не изменяют, CORS по умолчанию не открывать.
Локальный returnTo только из allowlist, без open redirect.
Вход и закрытые ответы: Cache-Control no-store. Не допускать утечки session
через логи, URL, HTML, JSON, error stack. CSRF/пароли и cookies редактировать в логах.
Ошибки БД наружу не передавать, транзакцию откатывать; отсутствие БД не выдавать
за пустой список или успешный вход. Health публично без конфигурации/секретов.
CSP сначала проверить на inline hero и style API, затем включить совместимый
строгий профиль; библиотеки/заголовки не являются доказательством безопасности.

Статика только /site и явные публичные страницы. Нельзя отдавать корень проекта,
.env, prisma, server, tools, документы и приватные файлы. Nginx тоже не должен
иметь независимый alias на весь репозиторий. Закрытые HTML защищены до send/render.
Доступ к /api проверяется независимо от того, доступна ли ссылка в интерфейсе.

— Поддерживаемые версии зависимостей и lock; установка с нуля по инструкции.
— Миграции на чистой PostgreSQL и повторный deploy без дублей; test DB отдельно.
