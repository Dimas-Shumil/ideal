1. ГРАНИЦЫ И СТЕК
Рекомендуется один модульный Node.js/Express-сервер, ESM, одна PostgreSQL,
Prisma для схемы и миграций. Без микросервисов, React, Redis и брокера на старте.
Точные поддерживаемые версии и совместимость закрепить lock-файлом на этапе 8,
а не считать установленными по памяти. Это выбор для IDEAL по будущим требованиям, а не копия стека источников.
Все три источника используют SQLite/Prisma 6 и CommonJS, не PostgreSQL/Prisma 7.
Небольшая однопроцессная установка SQLite у них не доказывает достаточность
для конкурентных записей и ledger IDEAL. ESM выбран для нового приложения,
а не обнаружен у доноров; CommonJS-утилиты потребуют явной адаптации. Все пути ниже — будущие, сейчас они не создаются.

server/app.js — сборка middleware и маршрутов; server/index.js — запуск/остановка.
server/config/env.js — проверка конфигурации без вывода значений секретов.
server/db/client.js — один клиент БД на процесс.
server/middleware/ — auth, permissions, csrf, errors, request-id, security.
server/modules/<module>/ — routes.js, service.js, schema.js;
repository.js выделять только при реальной сложности запросов.
Модули по очереди: auth/users (8), управление (9), trainers (10), clients и
memberships/attendance (11), schedule/bookings (12), notifications (13), shop (14).
server/views/ — будущие серверные шаблоны; отдельные layouts public/control/trainer.
prisma/schema.prisma и prisma/migrations/ — только реализуемые сущности этапа.
tests/ — проверки API, прав и транзакций на отдельной тестовой БД.
var/uploads/ — вне публичного корня и git; ops/ — будущие инструкции обслуживания.
Не создавать пустую инфраструктуру всех этапов заранее.

2. БАЗА ДАННЫХ
PostgreSQL предлагается из-за совместных записей владельца и тренеров,
конкуренции за последние места, балансы посещений и будущие остатки.
Нужны FK, уникальность, CHECK и транзакции; блокировка строки занятия позволяет
сериализовать проверку вместимости и создание записи в одной транзакции.
SQLite допустим при одном процессе и небольшом потоке записей, но усложнит
будущий переход типов и миграций. Не начинать production с SQLite лишь ради
простоты установки. Стоимость PostgreSQL — отдельное обслуживание и backup;
для разработки также PostgreSQL с теми же миграциями, не отдельная SQLite-схема.
База сама по себе не предотвращает переполнение: все пути записи, включая
админские операции, должны соблюдать одинаковый протокол транзакций.

4. АККАУНТЫ И ГРАНИЦЫ ДАННЫХ
Один клуб в одной установке — рабочее допущение до ответа владельца.
User — учётная запись сотрудника; TrainerProfile — публичные сведения тренера;
Client — посетитель клуба без обязательного User и без личного кабинета.
Роли-кандидаты OWNER и TRAINER. Сотрудник-администратор/кассир — только если
понадобится, не вводить всесильную STAFF заранее. Совмещение OWNER/TRAINER
и число владельцев согласовать перед фиксацией схемы роли.
Данные принадлежат клубу; createdBy не означает право собственности автора.
Содружество routes/personal.routes.js изолирует персоналки между OWNER
через ownerId, а общие спортсмены доступны всем владельцам. Транспортные
CRM src/routes/control.routes.js допускают только OWNER, клиенты общие.
Ни один проект не содержит готовых TRAINER-политик. Поэтому в IDEAL
данные клуба + назначения клиент/тренер, а не механическая замена OWNER
на TRAINER и не приватное владение клиентом по createdBy.
TrainerClientAssignment связывает тренера и клиента с периодом/статусом допуска.
Профиль TrainerProfile связан с User опционально: публичный тренер не обязан
иметь вход. Одна учётная запись тренера — не более одного профиля на старте.

Проверка TRAINER + принадлежность объекта обязательна на сервере в каждом
чтении/изменении/экспорте/вложении и в фоновых уведомлениях. trainerId брать
из аутентифицированного контекста, не доверять query/body. Списки, поиск,
счётчики и агрегаты фильтруются теми же условиями. Ответы — allowlist полей.
Для группового занятия тренер видит минимальный состав именно своего занятия;
это не открывает карточки и историю всех этих клиентов. Доступ к полной
минимальной карточке — только по активному назначению. После отзыва назначения
или деактивации права проверяются заново, кэш не должен оставлять старый допуск.
История посещений после смены тренера требует решения клуба; по умолчанию
не показывать тренеру чужую/бывшую историю. Публичный JSON никогда не содержит
контакты клиентов, служебные заметки, хеши паролей, сессии и push-endpoints.

6. РАСПИСАНИЕ, ЗАПИСЬ, ПОСЕЩЕНИЯ (11–12)
TrainingSession — конкретное занятие со startAt/endAt, типом, тренером,
вместимостью и статусом. Не записывать клиентов в абстрактный weekly-шаблон.
Повторы позже: шаблон порождает конкретные занятия с защитой от дублей;
изменение серии не переписывает проведённые занятия. Хранить время в UTC,
показывать в Asia/Krasnoyarsk; правила дня/временного окна считать по времени клуба.

Запись: транзакция блокирует занятие, проверяет статус/срок записи/места,
дубликат и право оператора; при резервировании посещения блокирует также
абонемент. Единый порядок блокировок, короткие транзакции, ограниченные повторы
после конфликтов. CHECK capacity > 0 и endAt > startAt, FK и уникальность.
Пересечения занятий тренера и занятость зала проверять в том же протоколе;
если вводится общий ресурс, блокировать его или применять ограничение интервалов.
Группа и персональная тренировка — один механизм экземпляров занятия с разными
правилами вместимости; не приравнивать персональное занятие к владельцу данных.
Booking: confirmed/cancelled; waitlist и pending только после согласования.
Attendance: present/absent, исправления через аудит и компенсирующую операцию.
Списание на записи или посещении, late cancel, no-show, заморозки и бонусный зал
пока не определены. Без ответов не реализовывать расчёт остатков абонемента.
Проверка остатка и его изменение атомарны; повтор HTTP-запроса не списывает дважды.
Сначала операторская запись. Публичная заявка, если нужна, отдельна от confirmed
booking; кабинет клиента и автоматическое подтверждение не согласованы.

  в семь публичных страниц; при SSR применять экранируемые partials.
— Для auth предпочесть express-session lifecycle по Содружеству, с PostgreSQL
  store и явной связью User. Его JSON Session и отзыв через contains не копировать.
  У транспортных Session полезны FK, idle/absolute и чтение active на запросе;
  весь их самописный cookie/token lifecycle не выбран автоматически.
— Новый store обязан поддерживать отзыв по userId и абсолютный срок независимо
  от rolling cookie. Проверить готовый совместимый адаптер; если эти требования
  не покрывает, документировать минимальную адаптацию, не писать криптографию.
— STAFF из транспортного enum не переносить: в коде он не имеет бизнес-доступа.
— Attendance upsert Содружества использовать как идею идемпотентности, но

  queue, dedup, claim, backoff, отмену устаревших jobs реализовать отдельно в 13.
